01 · Executive brief

What this system is

This repository implements a stateless HTTP service that checks for extractable text, converts PDFs into typed blocks in an inferred reading sequence, and returns the extracted document with a paragraph-message list and importance signals. The primary goal is text extraction; table and image extraction are additional capabilities.

Intended input

PDFs with extractable text, especially books and papers that should read in sequence.

Explicitly out of scope

Mostly scanned PDFs, including those with an OCR text layer. Visually complex born-digital layouts are accepted, though their reading order may need validation.

Implemented output

A validated Document with headings, paragraphs, tables, images, and code/formula blocks, plus each paragraph's text and detected importance signals.

Not implemented here

Segmentation, blob creation, LLM rewriting, persistence, authentication, and client-side asset storage.

Scope clarification: the README calls this a service that “turns a PDF into a validated Document,” but the actual /extract response also includes an importance object when eligible. The model file declares future pipeline contracts, but this repository does not implement those later stages.

Use this guide to decide what to trust and what to validate with real documents. Eligibility requires extractable text and no match to the mostly-scanned heuristic; it does not certify text completeness or reading order. A 200 response can mean the PDF was rejected by the eligibility gate; success is represented by the response body's eligible field.

when POST /extract receives an uploaded file:
  if the filename does not end in .pdf:
    return HTTP 400

  read at most 80 MiB + 1 byte
  if no bytes were uploaded: return HTTP 400
  if more than 80 MiB were read: return HTTP 413

  try to open the bytes as a PDF
  if opening fails: return HTTP 400
  if the PDF is encrypted: return HTTP 400

  if no page contains extractable non-whitespace text:
    return HTTP 200 with eligible=false and reason=no_text_layer
  if at least half of pages have images covering 70% or more of page area:
    return HTTP 200 with eligible=false and reason=scanned_document

  document = extract all pages into typed blocks
  importance = score paragraphs internally and keep only those scoring above 0.7
  return HTTP 200 with eligible=true, document, and importance

04 · Behavior

What the code actually computes

Eligibility gate: born-digital text, not page scans

check_eligibility first requires non-whitespace text on at least one page. It then counts pages containing an image that covers at least 70% of the page. If at least half the pages meet that test, it returns scanned_document, even if OCR made text extractable. A PDF with no extractable text returns no_text_layer. This geometric heuristic catches full-page scans with OCR text, but can miss partial-page scans and may reject a digital document whose pages are mostly full-page images.

Why there is no font/layout rejection: different font names, decorative pages, and vector artwork do not by themselves make text impossible to extract. Born-digital documents with unusual fonts or layouts are accepted and attempted. Font metadata still helps the extractor recognize bold text, code, and formulas; it does not determine scan eligibility.

Reading sequence is a separate quality goal. The extractor uses page coordinates and heuristics to order blocks, including a two-column guess. Passing the eligibility gate does not guarantee that sequence is right. Check extracted blocks in order on representative single-column, multi-column, and visually complex books; improve ordering without turning font variety into a rejection rule.

RuleCurrent settingInterpretation to verify

Language-neutral pseudocode · eligibility

function hasExtractableText(pdf):
        for each page in pdf, from first through last:
          text = ask PDF library for that page's text
          if text contains anything besides whitespace:
            return true
        return false

      if not hasExtractableText(pdf):
        reject with no_text_layer
      else if at least half of pages have an image covering 70% or more:
        reject with scanned_document
      else:
        continue to extraction

Important difference: this first asks whether any text exists anywhere, then rejects documents that look mostly like page scans. It does not check that every page has text or that every word was recovered. OCR is not performed by this service.

Block extraction

extract_document derives a document-wide body size and line pitch, detects repeated page furniture, and then processes each page. The page processor removes likely headers/page numbers, absorbs text contained in recognized tables and image regions, identifies captions, infers one- or two-column ordering, classifies lines, merges compatible adjacent lines, and constructs Pydantic block objects.

  • Headings: inferred from relative font size, boldness, uppercase styling, and numbering patterns. Heading hierarchy/level is not emitted.
  • Paragraphs: neighboring lines merge according to font size, vertical pitch, indentation, sentence-ending width, and bullet rules.
  • Tables: PyMuPDF's ruled-table detector is used; candidates need at least two rows and two columns and enough non-empty cells. Empty extracted cells normalize to empty strings.
  • Images: embedded raster images and selected clusters of vector drawings are clipped and rendered at 150 DPI to PNG data URIs.
  • Code: monospace-looking lines are joined with approximate indentation reconstruction, except when most document text is itself monospaced.
  • Formulas: selected math-font lines become formula-kind CodeBlocks with a cropped PNG. Extracted formula text is explicitly not the rendering source of truth.

What the layout terms mean

  • Page furniture means repeated page decoration such as a running header, footer, or page number. On PDFs with at least three pages, the extractor looks near the top and bottom 9% of each page for repeated text at a similar vertical position. Digits are normalized first, so changing page numbers can still match. Repeated candidates seen on at least three pages and roughly 40% of the document are removed. A real line repeated in the margin can be mistaken for furniture; a unique header may survive.
  • Line pitch is the typical vertical distance between the top coordinates of successive body-text lines from the same PDF text block, estimated as a median. It is not a word count or a font measurement. When two adjacent lines are considered for the same paragraph, a top-coordinate difference larger than about 1.35 times the estimated pitch (scaled for font size) starts a new block. If there are too few usable measurements, pitch defaults to 1.25 times body font size.
  • Image captions are not baked into the image. A nearby line beginning with a recognizable label such as Figure 2 or Fig. 2 is removed from the ordinary text lines and stored in ImageBlock.caption. It must be within about 45 PDF points above or below the image and overlap it horizontally. Unlabeled or farther-away captions may remain ordinary text or may not be associated with the image.
  • Table extraction asks PyMuPDF to detect table geometry and extract a grid of cell strings. A candidate is kept only if it has at least two rows and columns and at least 30% of its cells are non-empty. Blank cells become empty strings, and entirely blank rows are dropped. Text lines substantially inside the accepted table are removed from the normal text stream to avoid duplicate text. The result is a TableBlock with rows and an optional nearby labeled caption; cell styling, merged-cell meaning, and visual fidelity are not preserved.

How ordering handles lines: PyMuPDF first combines spans that it considers part of one text line. In a page not classified as two-column, the resulting text lines and visual items are sorted by their top Y coordinate, then their left X coordinate. The extractor does not cluster separate items whose Y coordinates are merely close into an approximate shared line. So same-height items are ordered left-to-right only when their top coordinates tie; small coordinate differences can put the slightly higher item first. A two-column page uses a separate midpoint/band heuristic: generally left column, then right column within each band. Neither path understands reading intent, so inspect complex pages.

Block length is not fixed. A paragraph block is formed by merging adjacent compatible text lines until spacing, indentation, font, punctuation, bullets, or another item suggests a boundary. There is no maximum number of words, characters, or tokens. For ordinary prose, a paragraph-shaped block might often be around 50–150 words, but that is only a rough writing convention, not a measured guarantee or a setting in this code. A long paragraph can produce a long block, and imperfect PDF spacing can merge or split paragraphs unexpectedly.

Practical chunk-size starting point: “block” means an extracted structural item; “chunk” means a later unit chosen for search or a model prompt. This repository does not implement chunking. As an initial downstream experiment, try about 300–600 words per semantic chunk (roughly 400–800 English tokens, with substantial variation), keep headings with their text, and avoid splitting a paragraph unless it is unusually long. Measure answer quality and prompt limits on your own material before treating that range as a requirement.

Ordering and classification are inferences over PDF coordinates and font metadata. The model guarantees non-decreasing page numbers, but not that block order within a page matches a reader's intended sequence. A complex layout should produce an extraction to inspect, not an automatic eligibility rejection.

Language-neutral pseudocode · PDF to blocks

function extractDocument(pdf):
      read text lines and image locations from every page
      estimate common body-text size and line spacing for the whole PDF
      find repeated headers and footers
      outputBlocks = []

      for each page in page-number order:
        remove likely repeated headers, footers, and page numbers
        find ruled tables; extract their cell text and nearby captions
        find raster images and likely diagram regions
        remove text lines already covered by an extracted table or image
        pageItems = remaining text lines + tables + images
        order pageItems by their page coordinates

        for each text line in that order:
          if it looks like code: classify as code
          else if it uses a recognized math font: classify as formula
          else if size, boldness, or numbering suggests a heading:
            classify as heading
          else:
            classify as paragraph

          join it to the previous block only if type, spacing,
          font size, indentation, and position look compatible
          otherwise finish the previous block and start a new one

        finish the last open text block on this page
        append the page's blocks to outputBlocks

      return Document(metadata, outputBlocks)

“Remove text lines covered by a table/image” avoids returning the same visible content twice. Tables and images are inserted into the same ordered block stream as text, so the reader can walk the page in sequence. The actual code has more geometric checks; this is the decision outline.

How the two-column guess works

if enough text lines sit on both sides of the page midpoint:
      mark lines spanning across the midpoint as possible separators
      split the page into vertical bands at those separators
      within each band, read the left column, then the right column
      keep separator lines in their vertical position
    else:
      sort items from top to bottom, then left to right

This is a geometric guess, not a semantic understanding of the page. Sidebars, marginal notes, tables, and unusual layouts can still be interleaved incorrectly. The reliable way to review it is to compare the ordered block text with the page itself.

High-scoring paragraph messages and the Q&A goal

The eligible response's importance.passages array contains only paragraph blocks whose internally calculated importance score is strictly greater than 0.7, ordered from highest score to lowest. The score is not included in the response. Each returned passage contains its source block_id, full paragraph text in message, and detected signals. The cutoff is a starting default, not a validated measure of educational value; tune it against labeled examples from your books.

The internal score combines normalized centrality with a 0.30 boost for a definition-like phrase and a 0.15 boost for a paragraph immediately after a heading, capped at 1.0. Signals describe which cues fired. The service returns qualifying paragraphs individually; it does not merge neighboring paragraphs into larger passages.

Important for your feature: the cutoff filters paragraphs, but it does not prove they are useful for Q&A. Measure missed and irrelevant passages on real examples before relying on the default. The chunk-size range above remains a separate downstream starting point if you later combine paragraphs.

Recommended next step: label useful and unhelpful paragraphs in representative books, compare them with the selected output, and adjust MIN_IMPORTANCE_SCORE based on missed and irrelevant results. Keep selection separate from PDF parsing so you can tune it without changing extraction.

Language-neutral pseudocode · current importance response

for each Paragraph block in document:
      score = min(1.0, 0.7 * centrality + definition_boost + position_boost)
      if score <= 0.7: skip this paragraph
      message = the paragraph's full text
      signals = []
      add centrality signal
      if text matches a definition phrase: add definitional signal
      if paragraph immediately follows a heading: add positional signal
      emit paragraph block ID, message, and signal names
      do not include the numeric score in the response
05 · Data contracts

The data contract, without the jargon

A “data contract” is the agreed shape of data passed between parts of the system: field names, value types, and rules that must hold. It lets the extractor, API, and later features agree on what they receive. It is not a separate service or a cache.

In this code, Document is the Python/Pydantic model for one PDF extraction result. It contains file metadata and an ordered list of blocks. A block is one extracted item: a heading, paragraph, table, image, or code/formula. Each block gets an ID so another result can point back to that exact source item. For example, an importance result can say “this message comes from block abc123.”

One PDF
  Document
    meta: filename, page count, title
    blocks:
      [block id, page, type, content]
      [block id, page, type, content]
  importance:
    [paragraph block id, message text, signals]

Language-neutral pseudocode · following a block reference

for each importance result:
    find the Document block whose id equals result.block_id
    use that block's paragraph text as the source passage
    keep the message and signal names beside it

  The importance result points to the text; it does not copy or replace it.

“Document population” means the collection/type of input PDFs this service is intended to handle, not a Python class or group of data records. The goal is born-digital PDFs with extractable text, particularly books and papers whose content can be read in sequence. Mostly scanned PDFs are rejected, including scans with an OCR text layer. Font or layout complexity alone is not out of scope.

The model file currently mixes schemas used by this service with schemas sketched for possible later stages. You do not need those future models to understand today’s endpoint.

Model familyRole in the intended pipelineImplemented here?
Document / BlockExtracted content and its metadata.Yes; emitted by the endpoint.

Recommendation for your one-shot workflow: if a book is uploaded, processed, sent to the next feature, and then discarded, you do not need a cache system or frozen Python objects just for caching. Keep one Document as the source of truth while that request is being processed; have importance/passage results refer to its block IDs. Avoid changing extracted block content after creating those results, because their IDs point to the original blocks. When the request ends, discard the in-memory objects. Persist only if the product later needs saved books, retry/resume, or repeat Q&A without re-uploading.

extraction_version is still useful as provenance (“which extraction logic made this?”), even without caching, but it does not by itself create a cache. Keep it if downstream logs or results need that traceability. The many Section, Blob, and processed-piece models are not used by this service today; to make the design easier to work with, consider moving these future-only schemas out of the active extraction contract until a real stage needs them.

Validation currently enforces unique block IDs within a document, non-decreasing page order, non-empty future sections/blobs/pieces, non-empty formula assets, and consistency between eligibility and rejection reasons. You can think of these as guardrails on the data shape. Additional cross-checks, such as whether referenced block IDs actually exist, are only needed if those future reference-based stages are implemented.

06 · Reliability boundaries

What confidence should mean here

Eligibility requires at least one page with non-whitespace extractable text and rejects documents when at least half their pages contain images covering 70% or more of page area. This scan check is heuristic: partial-page scans can pass, and a born-digital document dominated by full-page images can be rejected. It does not prove that all text was found. The extractor separately uses layout heuristics to order content, so sequence quality must be measured on representative documents rather than inferred from an eligible response.

HeuristicImportance cutoff needs evaluation

The current implementation returns only paragraphs with scores above 0.7, but that default has not been calibrated against human-labeled examples. The numeric score stays internal; the response includes only passage text, source IDs, and signals. Adjust the cutoff using missed and irrelevant passage rates from representative books.

Behavior gapSelected paragraphs are not grouped

The threshold filters individual paragraphs, but neighboring selected paragraphs are not combined and the current signals do not establish that a passage answers a question. Add and evaluate passage grouping separately if downstream Q&A needs larger coherent units.

Coverage gapTests validate one fixture more than the service boundary

Current tests cover fixture extraction, scanned-PDF rejection, acceptance of text with varied fonts/vector drawing, block page ordering, base64 image assets, JSON round-trip, and a small importance case. They do not yet prove complete text recovery or correct within-page sequence for multi-column and visually complex documents, nor do they exercise FastAPI responses, file limits, or latency/memory limits.

OperationalCPU, memory, and response size depend on document content

The route uses a synchronous handler for CPU-bound PyMuPDF work, and upload size is capped. However, rendered image/formula crops are embedded as base64 in JSON; an 80 MiB input limit does not cap output size or extraction time. Base64 also makes each binary image larger in the JSON response.

Practical fix: first measure representative books. Add limits for page count, individual/total rendered asset pixels or bytes, and total response size; return a clear “too large/unsupported” result when exceeded. Record per-stage time, peak memory, input bytes, page count, and output bytes. Set worker concurrency based on those measurements. If jobs are too slow for a normal request, then move processing to a bounded job queue; do not add a queue before latency evidence calls for it.

OperationalParser resources and errors need clear boundaries

The route opens a PDF for eligibility and the extractor opens it again; the code does not explicitly close these PyMuPDF document handles. Also, unexpected eligibility or importance-result failures sit outside the extraction-specific error handler.

Practical fix: close each parser deterministically (for example, with a context manager or finally), handle errors at the request boundary, log the failing phase with a request ID, and return a generic client-safe 500 message rather than exception internals. Keep the detailed exception in server logs.

OperationalHealth status is only a liveness check

/health returns “ok” without checking whether the service can open a PDF or has capacity. That is adequate as a basic liveness endpoint, but it does not prove extraction readiness.

Practical fix: keep liveness cheap. Add a separate readiness check only if deployment needs one, and make it check minimum real dependency state without parsing a large document on every probe.

BoundarySome work is outside the route's extraction error handler

Eligibility runs before the extraction try; importance-result generation runs after it. Unexpected exceptions in either phase are not converted by the route's explicit error handling into its documented extraction-specific HTTP 500 path. Decide whether generic server errors are acceptable and whether logs/metrics need phase context.

08 · A practical review method

Review the code in the order behavior happens

  1. Set the boundary. Read the README and requirements first. Write down supported PDFs, explicit non-goals, response shape, runtime version, and dependency/licensing constraints. Separate stated intent from verified implementation.
  2. Trace one request. Start in main.py. Follow an upload through validation, eligibility, extraction, importance-message generation, response serialization, and each HTTP failure path. Note where exceptions are caught and what resources are held.
  3. Understand the contract before the heuristics. Read the block union and validators in document_model.py. For every produced field, ask who consumes it, what invariant is enforced, and whether version/ID references can become stale.
  4. Follow the data shape through extraction. In extractor.py, track a page from PDF spans to line records to ordered items to typed blocks. Inspect each classifier and merge rule against examples; distinguish coordinate evidence from assumptions about reading order.
  5. Audit the text check, then audit sequence separately. Confirm that any extracted non-whitespace text on any page passes. Then inspect emitted block order against the PDF on single-column, multi-column, and mixed-layout examples; do not treat layout complexity itself as a reason to reject.
  6. Check claims against operations. Compare docstrings, README, response models, and actual calculations. This catches the response-field mismatch, mutable-versus-immutable contract, and TF-IDF-versus-term-frequency discrepancy found in this pass.
  7. Map tests to risks. Identify which requirement each test proves, then list untested behavior. Prefer a small test that fails for the suspected defect: API contract test, model mutation test, caption boundary test, or message/signal output test.
  8. Make one change and re-run the narrow check. Preserve the fixture baseline, add a regression case for the behavior being changed, then run the full suite and a representative request. For heuristic edits, compare block sequence/content and acceptance decisions, not just absence of exceptions.
  9. Decide with production evidence. Before changing thresholds or claiming extraction quality, evaluate against a labeled corpus and profile realistic files. Track acceptance/rejection, block-level accuracy, response bytes, latency, and failures by document type.

Review questions for every proposed change

  • Does this change affect the public response or only an internal heuristic?
  • Could it change block IDs, ordering, page attribution, asset output, or which passages reach Q&A?
  • What is the concrete wrong result today, and what test reproduces it?
  • Which supported document examples improve, and which may regress?
  • Does the change alter rejection behavior, response size, CPU, memory, or worker concurrency?
  • Are docs, schema, implementation, and downstream assumptions still consistent?
  • What result would make us revert or revise this decision?
